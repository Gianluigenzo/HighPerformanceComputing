### Exercise 1 - 'Parallel' Pragma
Simple exercise made to explore the usage and functionality of `#pragma omp parallel` and a few other constructs.
- exercise1.c
```C
void exercise(){
	int tid = 0, nthreads = 0;
	printf("I am thread number %d out of %d!\n", tif, nthreads);
}
```

The objective is to simply create a parallel section, with the desired number of threads, inside of this function. Then, using `omp_get_thread_num()` and `omp_get_num_threads()`, get to know the execution order for the team of threads that executes `print()`.

- **Solution**
```C
void exercise(){
	#pragma omp parallel num_threads(NTHREADS)
	{
		int tid = omp_get_thread_num(); 
		int nthreads = omp_get_num_threads();
		printf("I am thread number %d out of %d!\n", tif, nthreads);
	}
}
```

>[!Note]
>`NTHREADS` is a macro defined at compile time. Compilation happens via Makefile with the following command: `make EXERCISE=exercise1.c EXT_CFLAGS="-DNTHREADS=4" clean all run`.

### Exercise 2 - Loop parallelization
Usage of `#pragma omp for` directive and `#pragma omp schedule(...)` clause.

All the following sub-exercises start from the same for loop:
```C
for(int i = 0; i < NITERS; i++){
	work(W);
}
```

In the previous exercise `#pragma omp parallel` was used to create a parallel section for a certain section of code, this meant that the section was replicated for each thread and the code executed `NTHREADS` times. To achieve a `for` loop parallelization in the sense that the `NITERS` are divided among all the working threads, the `#pragma omp for` directive is needed:
```C
#pragma omp parallel for num_threads(NTHREADS)
for(int i = 0; i < NITERS; i++){
	work(W);
}
```

Starting from this result, the next exercises will exploit different modes of the `schedule(static)` clause to achieve different execution results.
#### Exercise 2a - Static Loops
Use of `schedule(static)`:
```C
#pragma omp parallel for num_threads(NTHREADS) schedule(static)
for(int i = 0; i < NITERS; i++){
	work(W);
} // implicit barrier (could be specified with #pragma omp barrier)
```
![[openmp-basics-2a-spec1.png|281]] Assuming $NITERS = 16$.

`schedule(static)` is optimal if the workload is balanced between each iteration, as there's a very little overhead (the scheduling is computed only once when reaching the `for` loop). Each thread will execute $M = \frac{NITERS}{NTHREADS}$ iterations.
#### Exercise 2b - Dynamic Loops
Use of `schedule(dynamic, CHUNK_SIZE)`:
```C
#pragma omp parallel for num_threads(NTHREADS) schedule(dynamic, M)
for(int i = 0; i < NITERS; i++){
	work(W);
} // implicit barrier (could be specified with #pragma omp barrier)
```

`schedule()` clause with `dynamic` requires the specification of an additional parameter which is the chunk size $M$, better explained as the number of iteration each thread will execute before checking again how main iterations are left to do. An overhead will be present before *AND* after $M$ iterations:
![[openmp-basics-2b-spec1.png|320]] ![[openmp-basics-2b-spec2.png|320]]

Still assuming $NITERS = 16$; the two images show the usage of `schedule(dynamic, M)`, with $M = \frac{NITERS}{NTHREADS}$ and $M = 1$ respectively.
- The first one produces the same effect of using `schedule(static)` except for the second overhead at the end of the $M$ iterations; 
- The second one shows the finest granularity possible with `schedule(dynamic, M)`.
Clearly these two examples are of use for this case of balanced workload.

### Exercise 5 - Task parallelism (Sections)
- code
```C
void sections() { 
	work(1*(1<<15)); 
	printf("%hu: Done with first elaboration!\n", …); 
	work(2*(1<<15)); 
	printf("%hu: Done with second elaboration!\n", …); 
	work(3*(1<<15)); 
	printf("%hu: Done with third elaboration!\n", …); 
	work(4*(1<<15)); 
	printf("%hu: Done with fourth elaboration!\n", …); 
}
```

The exercise asks to implement parallelization using different methods:
- **The first method** is doing something similar to the first exercise. By combining the use of `#pragma omp parallel`, `omp_get_thread_num()` and `if`/`else`, you get asked to achieve SPMD parallelization.
```C
void sections() {
    #pragma omp parallel num_threads(4) 
    {
        int tid = omp_get_thread_num(); 
        if(tid == 0){
            work(1 * (1<<15));
            printf("%hu: Done with first elaboration!\n", tid);
        }
        else if(tid == 1){
            work(2 * (1<<15));
            printf("%hu: Done with second elaboration!\n", tid);
        }
        else if(tid == 2){
            work(3 * (1<<15));
            printf("%hu: Done with third elaboration!\n", tid);
        }
        else if(tid == 3){
            work(4 * (1<<15));
            printf("%hu: Done with fourth elaboration!\n", tid);
        }
    }
}
```
- **The second method** is implementing the same workload partitioning with the `sections` directive.
```C
void sections() {
	#pragma omp parallel sections num_threads()
	{
		#pragma omp section
		{
			work(1*(1<<15)); 
			printf("%hu: Done with first elaboration!\n", omp_get_thread_num());
		}
		#pragma omp section
		{
			work(2*(1<<15)); 
			printf("%hu: Done with second elaboration!\n", omp_get_thread_num());
		}
		#pragma omp section
		{
			work(3*(1<<15)); 
			printf("%hu: Done with third elaboration!\n", omp_get_thread_num());
		}
		#pragma omp section
		{
			work(4*(1<<15)); 
			printf("%hu: Done with fourth elaboration!\n", omp_get_thread_num());
		} 
	}
}
```

These two basically do the same exact thing. The first can be considered as an "hardcoded" version of the second; so, the first one may be a bit faster as it has slightly less `pragma` overhead, but the second one is much more flexible. 
>[!Note] 
>Both these solutions suffer from some threads having idle time at the implicit barrier, given by the longer work times of other threads. For this specific exercise there is no way of avoiding that, but assuming you have many more iterations, you could just put them in a `for` loop and parallelize it using `#pragma omp parallel for schedule(dynamic, 1)`, OR by using task parallelism -> next exercise.
### Exercise 6 - Task parallelism (Task)
As anticipated, this exercise presents the "rolled-up" version of the previous.
- code
```C
void tasks(){
	unsigned int i;
	
	for(i = 0; i < 4; i++){
		work((i + 1)*1e6);
		printf("%hu: Done with elaboration\n", …);
	}
}
```

It is asked to distribute the workload among four threads using `task` directive.
- **Solution!**
```C
void tasks(){
	unsigned int i;
	#pragma omp parallel num_threads(4)
	#pragma omp single nowait
	for(i = 0; i < 4; i++){
		#pragma omp task firstprivate(i)
		{
			work((i + 1)*1e6);
			printf("%hu: Done with elaboration\n", omp_get_thread_num());
		}
	}
}
```

The main points of this solution are `#pragma omp task`, which is used pretty much as one could expect; after directing the compiler to create a parallel section with the specified number of threads, the `task` directive simply needs to wrap the section of code that needs parallelization.

This considered, the `#pragma omp single` directive is also needed to let the compiler know that the `for` loop must be executed by a single thread, while others skip it and jump directly to the parallel section's barrier, otherwise each thread would execute the `for` loop entirely. The `nowait` clause simply helps avoid redundant synchronization; `#pragma omp single` directive creates an implicit barrier at the end of its block, another barrier is already there by the action of `#pragma omp parallel`.

>[!Important] How does task parallelism actually work?
>`task` packages the unit of code inside brackets and pushes it into a queue, letting the `for` loop proceed without waiting for the execution of that code. The tasks inside the queue are then taken by available threads and executed asynchronously.

Lastly, a note regarding the `firstprivate()` clause (for usage check [[Parallel Programming with OpenMP#Data Scoping Clauses|here]]).
In the original solution `firstprivate()` is omitted and I'm not sure why, it's a bug probably.
The problem in omitting `firstprivate()` is the fact that $i$, being declared outside the parallel section, is a shared variable among all working threads. This means that while a task is waiting to be pulled from inside the queue, the value of $i$ could change and then the execution wouldn't follow the same logic as its sequential version. `firstprivate()` lets each working thread have their own private copy of $i$ with the value it had when the task was created (more specifically when the clause was encountered).

>[!Note]
>There would be no problem in omitting `firstprivate()` if $i$ was declared inside the `for` loop (`for(unsigned int i = 0; i < 4; i++)`), as it would be a firstprivate variable for the thread that executes the loop, hence it would default to `firstprivate` for all other threads too.
