### Exercise 1 - Saxpy
First use of `#pragma omp target`. `target` is used to send workload from the CPU thread to other devices' threads (which in most cases are GPUs).
![[openmp-am-1-spec1.png]] 

- saxpy.c
```C
/* * 2. saxpy on accel */ 
clock_gettime(CLOCK_REALTIME, rt + 0); 

for (int i = 0; i < n; i++) { 
	z[i] = a * x[i] + z[i]; 
}
 
clock_gettime(CLOCK_REALTIME, rt + 1);
wt = (rt[1].tv_sec - rt[0].tv_sec) + 1.0e-9 * (rt[1].tv_nsec - rt[0].tv_nsec); printf("saxpy on accel: %9.3f sec %9.1f MFLOPS\n", wt, 2.0 * n / (1.0e6 * wt));
```

Like already mentioned, the objective here is to transfer the workload of the function above to GPU threads. `#pragma omp target` alone is not enough because other devices do not have access to the memory addresses that store the variables of the main code. For this purpose the `map()` clause comes into play (explained [[Parallel Programming with OpenMP#Device and Mapping Clauses (used with `target` and `teams`)|here]]).

```C
/* * 2. saxpy on accel */
clock_gettime(CLOCK_REALTIME, rt + 0);

#pragma omp target map(to:x[0:n]) map(tofrom:z[0:n])
for (int i = 0; i < n; i++) {
	z[i] = a * x[i] + z[i];
}

clock_gettime(CLOCK_REALTIME, rt + 1);
wt = (rt[1].tv_sec - rt[0].tv_sec) + 1.0e-9 * (rt[1].tv_nsec - rt[0].tv_nsec); printf("saxpy on accel: %9.3f sec %9.1f MFLOPS\n", wt, 2.0 * n / (1.0e6 * wt));
```

>[!Note]
>Scalar values ($a$ and $n$ in this case) are automatically treated as firstprivate and as such are passed by value to the device threads.

What we get from executing this code is a massive **speed-down**, caused by the fact that this code is transferring the workload from the host thread (a CPU thread) to a device thread (in our case a CUDA thread), which, taken singularly, is much less "powerful" than the host thread. By creating a parallel section (`#pragma omp parallel for`) the execution time **halves**. This second solution is still too slow.
- **Performance graph for the first two solutions.**
![[openmp-am-1-spec2.png|426]]

>[!warning]
>The reason why `parallel` doesn't provide as much as a good speedup as in typical scenarios resides in the way GPUs are built. GPUs are composed of one or more *Streaming Multiprocessors*, (*SMs*). Threads are organized into *threadblocks*.
>Threads that belong to the same threadblock run on a SM and are able to synchronize, while those that are on different threadblocks can't.
>`#pragma omp target parallel for map(...) map(...)` creates a single team of threads on the GPU which corresponds to one threadblock, so a single SM is employed in executing the code.
