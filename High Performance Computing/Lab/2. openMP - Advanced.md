### Exercise 1 - Pi
**Use of critical, atomic, reduction clauses.**
The following exercise calculates an estimation of $\pi$ by the following formula: $$f(x) = \frac{4.0}{(1 + x^2)}$$ 
- pi.c
``` C
double pi;
for (int i = 0; i z NSTEPS; i++)
{
	double x = (i + 0.5) * dx;
	pi += 1.0 / (1.0 + x * x);
}
```

The obvious thing to try first is declaring a `#pragma omp parallel for` right outside the `for` loop. Clearly it's not possible to do that alone because there would be race conditions on the shared variable $pi$. Which is shared by default, being declared outside the loop.
To avoid such problem, both `#pragma omp critical` and `#pragma omp atomic` may be valuable alternatives. 

- **Solution with `critical`**
```C
double pi;
#pragma omp parallel for
for (int i = 0; i z NSTEPS; i++)
{
	double x = (i + 0.5) * dx;
	#pragma omp critical
	pi += 1.0 / (1.0 + x * x);
}
```

>[!Question]
 Q: Is the `for` clause really needed? YES. 
 A: By limiting the statement to `#pragma omp parallel`, a parallel section would be created in which each available thread operates the `for` loop $NSTEPS$ times. Using `#pragma omp parallel for` will instead create a parallel section in which each available thread executes $\frac{NSTEPS}{N\_THREADS}$ iterations.

`#pragma omp critical` creates a lock on the shared variable $pi$ in order to avoid race conditions.
By comparing the execution time of this solution with the original's sequential execution time, we observe a **much worse** performance! Explained later on.

The next solution, that employs `#pragma omp atomic`, does a really similar thing.
- **Solution with `atomic`**
```C
double pi;
#pragma omp parallel for
for (int i = 0; i z NSTEPS; i++)
{
	double x = (i + 0.5) * dx;
	double tmp = 1.0 / (1.0 + x * x);
	#pragma omp atomic
	pi = pi + tmp;
}
```

The effect of `#pragma omp atomic` is basically the same as that of `#pragma omp critical`. The main difference between the two is that `critical` creates a lock on entire sections of code (or complex operations that employ multiple reads and writes from different memory addresses), while `atomic` can be only used on elementary operations. `critical` proves to be much more flexible than `atomic`, but that comes at the cost of a bigger overhead. 
So, execution time-wise, `atomic` is faster than `critical`, but somehow is still slower than the initial sequential execution time. This is because both `atomic` and `critical` generate $NSTEPS$ overheads.

The next solution makes it possible to not have any overhead at all inside the `for` loop.
- **Solution with `reduction`**
```C
double pi;
#pragma omp parallel for reduction(+:pi)
for (int i = 0; i z NSTEPS; i++)
{
	double x = (i + 0.5) * dx;
	pi += 1.0 / (1.0 + x * x);
}
```

What `reduction` does is creating a private copy of the shared variable $pi$ for each thread. These copies are then summed - **(+, pi)** - at the end of the `for` loop. No pragmas inside the loop means no overheads generated at each iteration.

- Performance graph for each solution. The last solution has a speedup of $N\_THREADS$ w.r.t. the sequential execution.

### Exercise 2 - Fibonacci
**Parallelization of a recursive function.**
The following exercise calculates the value of the Fibonacci sequence given the index $n$.
- fibonacci.c - Please note that some changes to the original exercise are needed in order for it to reach this state.
```C
int fib(int n){
	if(n < 2) return n;
	int x = fib(n - 1);
	int y = fib(n - 2);
	return x+y;
}

int main(int argc, char* argv[]){
	[...]
	fib(input);
	[...]
}
```

Pragmas used (other than those already checked out):
`#pragma omp task [clause]`
`#pragma omp taskwait`

>[!Note 1] 
Using `#pragma omp parallel` *inside* the recursion would mean creating a parallel section at each recursive function call. So, `#pragma omp parallel` is going to be inside the main function, before the first `fib` function call. 

>[!Note 2] 
We want a single thread to execute the first `fib` function call, so we are also going to use `#pragma omp single`. Other threads, involved in the parallelization, will be as shown later on.

- **First solution - NOT COMPLETE!**
```C
int fib(int n){
	if(n < 2) return n;
	int x, y;
	#pragma omp task shared(x)
	{
		x = fib(n - 1);
	}
	#pragma omp task shared(y)
	{
		y = fib(n - 2);
	}
	#pragma omp taskwait
	return x+y;
}

int main(int argc, char* argv[]){
	[...]
	#pragma omp parallel
	{
		#pragma omp single
		{
			fib(input);
		}
	}
	[...]
}
```

When declaring the creation of a task with `#pragma omp task` the compiler needs to know weather x and y need to be shared among the tasks or not. In the previous exercise the parallel execution was shared among threads, all of which "knew" the scope of the shared variable $pi$. This example is different because tasks do not know the scope of variables, so they need to be told in the `pragma` statement so they can all write in the same memory address avoiding memory problems.

The current solution still has a problem, which is the ever-multiplying number of tasks; every time a recursive function call takes place a new task is created.
![[openmp-adv-2-spec1.png]]
Practically speaking, the real problem resides in the fact that at a certain point a number of tasks $\ge$ than the number of threads will be created, and these tasks will just wait to be executed sequentially among the number of available threads (having pending tasks is simply of no use - and sometimes problematic if we consider memory usage).

Once enough tasks are created, employing all available threads, the creation of new tasks can be stopped using an 'if' condition (we use it as an additional clause for the pragma).
- **Second solution - STILL NOT COMPLETE!**
```C
int fib(int n){
	if(n < 2) return n;
	int x, y;
	#pragma omp task shared(x) if(n > CUTOFF)
	{
		x = fib(n - 1);
	}
	#pragma omp task shared(y) if(n > CUTOFF)
	{
		y = fib(n - 2);
	}
	#pragma omp taskwait
	return x+y;
}

int main(int argc, char* argv[]){
	[...]
	#pragma omp parallel
	{
		#pragma omp single
		{
			fib(input);
		}
	}
	[...]
}
```

While $n$ keeps above a certain CUTOFF value (in the exercise it is set at 20), the function will keep generating new tasks, then stops and executes sequentially. 

This solution already works properly but has a huge overhead problem. Let's consider the case of an execution with $n = 40$: the previous adjustments will have the function create 22000 parallel tasks (which corresponds to the number of recursive calls in the first 20 layers of the call tree). Each of these parallel tasks will then interrogate the pragmas on weather to create new parallel tasks or not. Very clearly it takes a lot of time to do this!

The problem can be solved by changing *where* the previous interrogation takes place.
- **Third solution - COMPLETE!**
```C
int serfib(int n){
	if(n < 2) return n;
	return serfib(n - 1) + serfib(n - 2);
}

int fib(int n){
	if(n < 2) return n;
	if (n <= CUTOFF) return serfib(n);
	int x, y;
	#pragma omp task shared(x)
	{
		x = fib(n - 1);
	}
	#pragma omp task shared(y)
	{
		y = fib(n - 2);
	}
	#pragma omp taskwait
	return x+y;
}

int main(int argc, char* argv[]){
	[...]
	#pragma omp parallel
	{
		#pragma omp single
		{
			fib(input);
		}
	}
	[...]
}
```
Now parallel tasks are created *by default* and, once a certain value of $n$ is reached, a purely sequential Fibonacci function will be called.

### Exercise 3 - Jacobi
The following exercise implements the Jacobi iteration. A step of the Jacobi iteration follows this formula: $$A_{k+1}(i,j)=\frac{A_k(i - 1, j)+A_k(i + 1, j)+A_k(i,j - 1)+A_k(i, j + 1)}{4}$$
- jacobi.c
```C
while(err > tol && iter < iter_max){ //convergence loop
	err = 0.0;
	
	for(int j = 1; j < n - 1; j++){ //calculate next
		for(int i = 1; i < m - 1; i++){
			Anew[j][i] = 0.25 * (A[j][i + 1] + A[j][i - 1] +
								 A[j - 1][i] + A[j + 1][i]);
								 
			err = max(err, abs(Anew[j][i] - A[j][i]));
		}
	}
	
	for(int j = 1; j < n - 1; j++){ //exchange values
		for(int i = 1; i < m - 1; i++){
			A[j][i] = Anew[j][i];
		}
	}
	iter++;
}
```

There are two different solutions slide-wise and lecture-wise.
#### Slide solution(s)
- **First solution - NOT COMPLETE!**
```C
while(err > tol && iter < iter_max){
	err = 0.0;
	
	#pragma omp parallel for reduction(max:err) -> creation of parallel threads
	for(int j = 1; j < n - 1; j++){
		for(int i = 1; i < m - 1; i++){
			Anew[j][i] = 0.25 * (A[j][i + 1] + A[j][i - 1] +
								 A[j - 1][i] + A[j + 1][i]);
								 
			err = max(err, abs(Anew[j][i] - A[j][i]));
		}
	}
	
	#pragma omp parallel for -> another creation of parallel threads
	for(int j = 1; j < n - 1; j++){
		for(int i = 1; i < m - 1; i++){
			A[j][i] = Anew[j][i];
		}
	}
	iter++;
}
```

This first solution lets us create a team of parallel threads for each `for` loop. Like it's already been seen before, we are doing the same operation multiple times, which, in terms of overhead, is not very effective.

- **Second solution - STILL NOT COMPLETE!**
```C
while(err > tol && iter < iter_max){
	err = 0.0;
	#pragma omp parallel -> single creation of parallel threads
	{
		#pragma omp for reduction(max:err) -> workload subdivision
		for(int j = 1; j < n - 1; j++){
			for(int i = 1; i < m - 1; i++){
				Anew[j][i] = 0.25 * (A[j][i + 1] + A[j][i - 1] +
									 A[j - 1][i] + A[j + 1][i]);
									 
				err = max(err, abs(Anew[j][i] - A[j][i]));
			}
		}
		#pragma omp barrier -> need to let all threads complete the first for loop
		#pragma omp for
		for(int j = 1; j < n - 1; j++){
			for(int i = 1; i < m - 1; i++){
				A[j][i] = Anew[j][i];
			}
		}
	}
	iter++;
}
```

Now we don't have unnecessary overheads, at the cost of having to create a barrier to let all threads finish their jobs on the first nested `for` loops. It comes as obvious that now there's a waiting element in the code that can be prevented by the next solution.

>[!Note]
>The barrier is explicit in this example, but in reality there should also be an implicit barrier after every `#pragma omp for` section.

- **Third solution - COMPLETE!**
```C
while(err > tol && iter < iter_max){
	err = 0.0;
	
	#pragma omp parallel for reduction(max:err)
	for(int j = 1; j < n - 1; j++){
		#pragma omp simd
		for(int i = 1; i < m - 1; i++){
			Anew[j][i] = 0.25 * (A[j][i + 1] + A[j][i - 1] +
								 A[j - 1][i] + A[j + 1][i]);
								 
			err = max(err, abs(Anew[j][i] - A[j][i]));
		}
	}
	
	#pragma omp parallel for
	for(int j = 1; j < n - 1; j++){
		#pragma omp simd
		for(int i = 1; i < m - 1; i++){
			A[j][i] = Anew[j][i];
		}
	}
	iter++;
}
```

The `simd` directive makes multiple iteration of the nested `for` loops execute at once.

#### Lecture solution
```C
while(err > tol && iter < iter_max){
	err = 0.0;
	#pragma omp parallel 
	{
		#pragma omp for collapse(2) reduction(max:err)
		for(int j = 1; j < n - 1; j++){
			for(int i = 1; i < m - 1; i++){
				Anew[j][i] = 0.25 * (A[j][i + 1] + A[j][i - 1] +
									 A[j - 1][i] + A[j + 1][i]);
									 
				err = max(err, abs(Anew[j][i] - A[j][i]));
			}
		}
		//as stated before, here is an implicit barrier
		#pragma omp for collapse(2)
		for(int j = 1; j < n - 1; j++){
			for(int i = 1; i < m - 1; i++){
				A[j][i] = Anew[j][i];
			}
		}
	}
	iter++;
}
```

The functionality of the `collapse()` clause can be found explained [[Parallel Programming with OpenMP#Loop Scheduling Clauses (used with `for`)|here]].

In most cases, the speedup provided by `#pragma omp simd` is much better. The cases in which `collapse()` proves to be the right choice are those in which $\#iterations\_outermost\_loop << \#iterations\_innermost\_loop$. This is because dedicating entire threads only to the execution of the outermost loops (which are smaller) will generate a lot of idle time in the threads employed (`collapse()` would prevent such problem at the root as it makes nested loops be seen as a single loop).
