### Exercise 1 - Saxpy
First use of `#pragma omp target`. `target` is used to send workload from the CPU thread to other devices' threads (which in most cases are GPUs).
![[openmp-am-1-spec1.png]] 

- saxpy.c
```C
/* * 2. saxpy on accel */ 
clock_gettime(CLOCK_REALTIME, rt + 0); 

for (int i = 0; i < n; i++) { 
	z[i] = a * x[i] + z[i]; 
}
 
clock_gettime(CLOCK_REALTIME, rt + 1);
wt = (rt[1].tv_sec - rt[0].tv_sec) + 1.0e-9 * (rt[1].tv_nsec - rt[0].tv_nsec); printf("saxpy on accel: %9.3f sec %9.1f MFLOPS\n", wt, 2.0 * n / (1.0e6 * wt));
```

Like already mentioned, the objective here is to transfer the workload of the function above to GPU threads. `#pragma omp target` alone is not enough because other devices do not have access to the memory addresses that store the variables of the main code. For this purpose the `map()` clause comes into play (explained [[Parallel Programming with OpenMP#Device and Mapping Clauses (used with `target` and `teams`)|here]]).

- **First solution - NOT COMPLETE!**
```C
/* * 2. saxpy on accel */
clock_gettime(CLOCK_REALTIME, rt + 0);

#pragma omp target map(to:x[0:n]) map(tofrom:z[0:n])
for (int i = 0; i < n; i++) {
	z[i] = a * x[i] + z[i];
}

clock_gettime(CLOCK_REALTIME, rt + 1);
wt = (rt[1].tv_sec - rt[0].tv_sec) + 1.0e-9 * (rt[1].tv_nsec - rt[0].tv_nsec); printf("saxpy on accel: %9.3f sec %9.1f MFLOPS\n", wt, 2.0 * n / (1.0e6 * wt));
```

>[!Note]
>Scalar values ($a$ and $n$ in this case) are automatically treated as firstprivate and as such are passed by value to the device threads.

What we get from executing this code is a massive **speed-down**, caused by the fact that this code is transferring the workload from the host thread (a CPU thread) to a device thread (in our case a CUDA thread), which, taken singularly, is much less "powerful" than the host thread. By creating a parallel section (`#pragma omp parallel for`) the execution time **halves**. This second solution is still too slow.
- **Performance graph for the first two solutions.**
![[openmp-am-1-spec2.png|426]]

>[!warning]
>The reason why `parallel` doesn't provide as much as a good speedup as in typical scenarios resides in the way GPUs are built. GPUs are composed of one or more *Streaming Multiprocessors*, (*SMs*). Threads are organized into *threadblocks*.
>Threads that belong to the same threadblock run on a SM and are able to synchronize, while those that are on different threadblocks can't.
>`#pragma omp target parallel for map(...) map(...)` creates a single team of threads on the GPU which corresponds to one threadblock, so a single SM is employed in executing the code.
#### Secondary device parallelization
There exist two directives that can be employed to distribute the workload among different GPU threadblocks:
- `#pragma omp teams`
- `#pragma omp distribute`
Both of these are explained [[Parallel Programming with OpenMP|here]], but here below is a visual representation of the outcome of the two directives.
![[openmp-am-1-spec3.0.png|330]]    ![[openmp-am-1-spec3.1.png|330]]

They basically have a pretty similar functionality to `#pragma omp parallel` and `#pragma omp for` respectively, with the exception that there is no way of synchronizing or knowing the execution order inside the threadblocks.

- **Third solution - COMPLETE!**
```C
/* * 2. saxpy on accel */
clock_gettime(CLOCK_REALTIME, rt + 0);

#pragma omp target teams distribute parallel for \
	num_teams(n/NTHREADS_GPU) thread_limit(NTHREADS_GPU) \
	map(to:x[0:n]) map(tofrom:z[0:n])
for (int i = 0; i < n; i++) {
	z[i] = a * x[i] + z[i];
}

clock_gettime(CLOCK_REALTIME, rt + 1);
wt = (rt[1].tv_sec - rt[0].tv_sec) + 1.0e-9 * (rt[1].tv_nsec - rt[0].tv_nsec); printf("saxpy on accel: %9.3f sec %9.1f MFLOPS\n", wt, 2.0 * n / (1.0e6 * wt));
```

>[!Note] 
>The solution proposed in slides differs a bit from the one proposed here, this version offers the same results with less redundancies (duplicated mappings, distribution scheduling...).
>It may be still worth to check the differences between the two so at paragraph's end will be proposed the original.

#### Old solution
```C
/* * 2. saxpy on accel */
clock_gettime(CLOCK_REALTIME, rt + 0);

	z[i] = a * x[i] + z[i];
}

clock_gettime(CLOCK_REALTIME, rt + 1);
wt = (rt[1].tv_sec - rt[0].tv_sec) + 1.0e-9 * (rt[1].tv_nsec - rt[0].tv_nsec); printf("saxpy on accel: %9.3f sec %9.1f MFLOPS\n", wt, 2.0 * n / (1.0e6 * wt));
```

The main redundancies of this version are:
- Mappings duplication, present in `#pragma omp target data` and `#pragma omp target teams`. More precisely, the whole `#pragma omp target data` line is redundant as that directive is only useful in cases where the `#pragma omp teams` directive needs to be used more than once;
- `num_threads(...)` and `dist_schedule(...)` clauses are more optimally (and automatically) calculated by `#pragma omp parallel for`, which is already present in the same directive call;
- All these pragmas may be called in the same line, as in [[3. openMP - Accelerator Model#Secondary device parallelization|this solution]]. 
Keeping everything is not wrong, but many of these directive's callouts have been optimized and made better in subsequent openMP versions.
### Exercise 2 - Matmul
As the name suggests, this function implements matrix multiplication.
```C
void gemm_acc(float* restrict a, float* restrict b, float* restrict c, int n){
	int bk / SM;
	
	for(int i = 0; i < bk; i++){
		for(int i = 0; i < bk; i++){
			for(int i = 0; i < bk; i++){
				float b2[SM * SM];
				reorder2(&b[SM * (k * n + j)], b2, n);
				kernel(&a[SM * (i * n + k)], b2, &c[SM * (i * n + j)], n);
			}
		}
	}
}
```

A way to optimize this code is doing the exact same thing that's been done for the previous exercise with just a few adjustments.
- **Solution**
```C
void gemm_acc(float* restrict a, float* restrict b, float* restrict c, int n){
	int bk = n / SM;
	#pragma omp target teams distribute parallel for collapse(3) \
		num_teams(bk/NTHREADS_GPU) thread_limit(NTHREADS_GPU) \
		map(to:a[0:n * n], b[0:n * n]) map(from:c[:n * n])
	for(int i = 0; i < bk; i++){
		for(int i = 0; i < bk; i++){
			for(int i = 0; i < bk; i++){
				float b2[SM * SM];
				reorder2(&b[SM * (k * n + j)], b2, n);
				kernel(&a[SM * (i * n + k)], b2, &c[SM * (i * n + j)], n);
			}
		}
	}
}
```

What's worth noticing in this solution is:
- `collapse(3)`: Used to "squeeze" the three nested `for` loops into a single, exponentially bigger one;
- The matrices are of shape $\#rows = \#columns = n$ so the mappings copy arrays of length $n \cdot n$.

The solution provides a much better speedup then it did for the previous exercise.
